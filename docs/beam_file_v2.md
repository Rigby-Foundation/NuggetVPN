# Технический анализ формата хранения и защиты профилей в Beam 2.0

## 1. Введение

В обновлении Beam 2.0 было заявлено «нативное шифрование профилей» с целью предотвращения чтения и миграции конфигураций сторонними инструментами. Данный документ описывает реальную архитектуру пайплайна чтения/записи, структуры данных и особенности криптографической модели, выявленные в ходе анализа бинарного файла.

---

## 2. Архитектурная цепочка (Data Pipeline)

Пайплайн работы с файлом конфигурации (`.beam`) состоит из четырёх последовательных уровней абстракции:

```
[Диск: файл .beam]
       │
       ▼ (1. Валидация заголовка)
Проверка длины (>= 5 байт) и сигнатуры версии (байт [4] == 0x04)
       │
       ▼ (2. DPAPI / Keystore Unprotect)
CryptUnprotectData с энтропией "beam.profile.store.v1" -> Мастер-ключ
       │
       ▼ (3. Симметричная дешифрация)
XChaCha20-Poly1305 (golang.org/x/crypto/chacha20poly1305)
       │
       ▼ (4. Распаковка)
gzip decompress (compress/gzip)
       │
       ▼ (5. Сериализация)
JSON parse -> Доменная модель профиля
```

---

## 3. Детальный разбор компонентов

### 3.1. Валидация заголовка и сигнатура формата (`decodeStorage`)
Процедура `beam_bridge_core_infrastructure_beam_decodeStorage` выполняет первичные проверки входного буфера:
* Проверяется минимальная длина слайса (`cmp rbx, 5; jl error`).
* Байт по смещению `+4` проверяется на равенство `0x04` (`cmp byte ptr [rax+4], 4; jnz error`). Это сигнатура формата хранилища версии 2.

### 3.2. Префикс строковых токенов (`decodeToken`)
Для сериализованных строковых представлений используется контейнерный формат с текстовым префиксом:
* Сигнатура: 7 байт `enc:v1:` (`3A636E65h` -> `enc:`, `3176h` -> `v1`, `3Ah` -> `:`).
* Полезная нагрузка после 7-го байта декодируется стандартным Base64 (`encoding_base64__ptr_Encoding_DecodeString`).

### 3.3. Криптографический примитив
В качестве симметричного шифра используется:
* **Алгоритм:** XChaCha20-Poly1305 (AEAD с 192-битным nonce и 256-битным ключом).
* **Реализация:** Пакет `golang.org/x/crypto/chacha20poly1305` (`NewX`).

### 3.4. Управление ключами (Key Derivation / Key Storage)
Ключ шифрования не генерируется из пользовательского пароля, а извлекается через системное хранилище Windows:
* Используется системный вызов Windows API **Data Protection API (DPAPI)**:
  * `CryptProtectData` (при сохранении).
  * `CryptUnprotectData` (при чтении).
* В качестве дополнительной энтропии (`pOptionalEntropy`) передаётся константная строка:
  ```
  "beam.profile.store.v1"
  ```

## 4. Архитектурный анализ безопасности

### Проблема модели угроз «Security through Obscurity»

Использование DPAPI без привязки к явному паролю пользователя (`CRYPTPROTECT_UI_FORBIDDEN` или отсутствие `CRYPTPROTECT_LOCAL_MACHINE`) означает следующее:
1. **Отсутствие изоляции процессов:** Windows DPAPI шифрует данные с использованием ключей текущей учётной записи пользователя (`User Credential Keys`).
2. **Прозрачность для локального ПО:** Любой процесс, исполняемый в контексте того же пользователя Windows, имеет легитимное системное право вызывать `CryptUnprotectData` с той же солью энтропии (`"beam.profile.store.v1"`).
3. **Отсутствие аппаратной изоляции:** Данные защищены от чтения другими пользователями ОС или при копировании на другую машину, но не изолированы от процессов внутри одной сессии пользователя.

---

## 5. Вывод

Формат профилей Beam 2.0 представляет собой стандартный сжатый JSON (Gzip), обёрнутый в контейнер XChaCha20-Poly1305, ключ которого защищён стандартным виндовым DPAPI с фиксированной константой энтропии. Данная схема обеспечивает защиту данных при краже файла на сторонний компьютер, однако не ограничивает доступ локальных приложений в рамках одной пользовательской сессии.
